制造云-数据库设计开发规范与多数据库适配要求

说明：本文档以之前智能制造数据库设计开发规范，加上平台多数据库适配新的要求整理。同时在本文档第六单将开发在制造云服务开发过程中违反规范碰到的各类数据库问题进行汇总，请各开发重点关注。

# 数据库设计规范

## 基础设置

- 【强制】(MySQL) 使用InnoDB存储引擎。
- 【强制】字符集使用UTF8（MySQL使用UTF8MB4）。
- 【强制】数据库语法设置为大小写不敏感。
- 【强制】数据库内容设置为大小写不敏感。实例和数据库排序规则：utf8_general_ci（MySQL全领域统一使用utf8mb4_general_ci，不设大小写敏感。 如果有业务需要大小写敏感，需要提申请进行审核）。近期全领域环境（公有云和专属化）环境都调整为了默认设置为（字符集utf8mb4\排序规则utf8mb4_general_ci)。所以以后新建表的脚本定义，**都不要再指定字符集和排序规则**。以前有部分优化，设置将平台（组织、部门）外键专门修改为ubf8的，要再去掉指定的字符集）。
- 【强制】字符集应保持一致，包括库默认字符集，表默认字符集，字段字符集。
- 【强制】所有表和字段都需要添加注释。对外公开的数据字典使用。

## 命名规范

### 基本原则

- 【强制】命名采用mysql方式，一律使用英文小写字母，以下划线连接各英文单词，在英文单词后可包含数字。
- 【推荐】命名应使用富有意义英文词汇或简写，不要使用n1、n2或拼音简写之类难以阅读的命名规则。
- 【强制】业务表名必须增加领域/应用标识前缀（参见模块代码表）。
- 【强制】库名、表名、字段名、索引名禁止超过30个字符（DB2索引名不超过18个字符）。
- 【强制】库名、表名、字段名、索引名禁止使用数据库保留字和关键字。
- 【强制】临时库、表名必须以tmp为前缀，如果是按照日期生成的，以日期为后缀（格式为yyyymmdd）。
- 【推荐】备份库、表建议以bak为前缀，如果是按照日期生成的，以日期为后缀（格式为yyyymmdd）。
- 【推荐】表的名称一般使用名词或者动宾短语，名词使用单数而不是复数形式，例如使用employee而不是employees。
- 【推荐】主子表的命名规范建议子表命名为主表名称加_detail后缀，子子表建议命名为主表名称加_subdetail后缀。
- 【推荐】为区分客开创建的数据表，建议增加cust_前缀或以企业名称的简写为前缀

##  设计规范

### 库、表、字段开发设计规范

- 【推荐】将变更频繁的数据和不频繁的数据分表存储，分离动静数据。
- 【推荐】采用合适的分库分表策略。可以参考ucf-cn规范里的1.2.10 分库分表
- 【推荐】(MySQL) 尽可能不使用TEXT、BLOB类型。
- 【推荐】(MySQL) 大字段例如varchar(2000)、TEXT、BLOB等字段最好独立分表，与主数据表分开存储。
- 【强制】(MySQL) 用DECIMAL代替FLOAT和DOUBLE存储精确浮点数。
- 【强制】文件图片等大数据使用公共文件服务器存储，数据库中存储文件服务器文件id。
- 【强制】禁止在数据库中存储明文密码，把密码加密后存储。
- 【强制】禁止使用触发器、函数、存储过程。（注：通版产品在遵守cn规范的情况下会获得多数据库方面的支持，但是项目化的客开产品/定制产品可能限定了数据库类型，出于成本或时间或复杂度的考虑，可灵活使用触发器、函数、存储过程等）。
- 【强制】禁止单条SQL语句同时更新多个表。
- 【推荐】除非数据集成或对外共享数据，否则不建议使用视图。
- 【推荐】尽量不要使用外键，影响性能且增加数据库维护难度，可以通过外围业务逻辑约束。
- 【推荐】引用类型的字段建议增加索引。
- 【推荐】建议所有字段均定义为NOT NULL。查询字段最好有默认值，null无法使用索引。（这个在mysql5.6后的版本有改进，可以在索引中使用空值（null），但只限于 is null语法，is not null是走不了索引的）。存在null值时，查询时会导致or拼接问题，在很多场景下会导致严重的效率问题。

### 主键

- 【强制】表必须有主键
- 【强制】禁止使用用户可以更新的列构成主键。禁止使用联合主键。
- 【推荐】业务主键需通过定义唯一性索引（或约束）来保证

### 索引

- 【推荐】索引的选择性是建立索引需要考虑的最重要原则，应尽量使得建立的索引具有最强的选择性
- 【强制】建立复合索引的原则是将选择性强的列依次放在前面
- 【强制】构成复合索引的列禁止超过5个
- 【强制】记录数不大于100的表禁止建立索引 
- 【推荐】对于操作频繁的表，原则上索引数目不要超过5个；普通操作频度的表，以不超过10个为宜
- 【推荐】(SQL Server) 推荐创建包含性列的索引，来达到覆盖索引的效果

# 数据库开发规范

## SQL编写规范

- 【强制】引用字符时用单引号，即update testable set idcol='abcd'
- 【推荐】连接符或运算符or、in、and、＝、<=、>=， +，- 等前后加上一个空格。
- 【推荐】不要使用select * …… 形式的语句，应指出select的具体字段，即select col1,col2,… from tablea where …
- 【强制】严禁使用 insert into table values(?,?,?)，必须指出具体要赋值的字段，即insert into tablea (col1, col2,…) values(?,?,…)
- 【强制】查询语句包含多表连接时，对每个字段的使用都要带上表别名，否则有子查询的情况下,语句可能出现执行计划错误,甚至结果集错误。即 select a.col1, a.col2, b.col3 from tablea a, tableb b where a.col4=b.col5。允许表名做别名的默认规则
- 【强制】避免隐含的类型转换。例如在where子句中DECIMAL型和INT型的列的比较或相加。
- 【强制】避免在where子句中对过滤字段使用函数，如：where IFNULL(name,’xx’) =’ss’。会影响索引的高效使用
- 【推荐】在子查询中前后应加上括号。
- 【推荐】避免在where使用'1=1','1=2'这种表达式作为部分条件，如 select col1, col2 from tablea where 1=1 and col1 >0

## 性能优化规范

- 【推荐】SQL语句尽可能简单，大的SQL想办法拆成小的SQL语句(充分利用QUERYCACHE和充分利用多核CPU)
- 【推荐】在进行多条记录的增加、修改、删除时，与数据库交互频繁，性能较差，建议使用批处理功能，批处理的次数以整个SQL语句不超过相应数据库的SQL语句大小的限制为准
- 【推荐】如果in的元素较多（超过300），可以使用in() or in ()的方式，超过2000时，建议分批进行查询。不推荐使用临时表，如果必须使用临时表的场景，需要注意做好事务管理。
- 【强制】禁止使用or 超过 500个。
- 【强制】禁止使用not in 语句，建议用not exist
- 【强制】禁止在一条SQL语句中使用3层以上的嵌套查询，如果有，请考虑使用中间结果集或临时表。（临时表需要注意做好事务管理）
- 【推荐】尽量避免在一条SQL语句中从>= 4张表中同时取数，如果必须关联4个或4个以上表，尽量采用子查询的方式
- 【推荐】尽量避免使用order by和group by操作，因为大量的排序分组操作影响系统性能。如必须使用，尽量建立在有索引的列上
- 【推荐】对索引列的比较，尽量避免使用NOT 或 !=，可以考虑拆分为几个条件。如col1 是索引列，条件col1 !=0 可以拆分为col1 >0 or col2 <0
- 【推荐】任何对列的操作都将导致表扫描，例如函数、计算表达式等，所以应尽量将数据库函数、计算表达式写在逻辑操作符右边
- 【推荐】在对char类型比较时,建议不要使用trim()函数,应该在程序中将不足的长度补齐
- 【推荐】用多表连接代替复杂EXISTS子句
- 【推荐】如果有多表连接时，应该有主从之分，并尽量将筛选条件放在主表上，被关联表的关联字段，一般也要建立索引。如select a.col1,b.col2 from a join b on a.col3=b.col4 where a.col5 = ‘a’
- 【推荐】读写分离的库，纯写库应尽量避免不必要的索引。
- 【推荐】用WHERE子句替换HAVING子句，避免使用HAVING子句作为条件。HAVING只会在检索出所有记录之后才对结果集进行过滤，而这个处理需要排序、总计等操作。如果能通过WHERE子句限制记录的数目,那就能减少这方面的开销。HAVING中的条件一般用于对一些几何函数的比较，如COUNT()等等，除此而外,一般的条件应该写在WHERE子句中。例如，select count(a),b from table1 where a=1 group by b having b=2 请修改为select count(a),b from table1 where a=1 and b =2 group by b
- 【推荐】避免在索引字段上使用表达式或函数。因为索引结构决定，WHERE子句中，如果在索引字段上使用表达式、函数或隐式数据类型转换，将会造成无法使用该字段上的索引
- 【推荐】不要在子查询中引用主查询的条件
- 【推荐】MySQL尽量避免用数据库进行复杂的业务逻辑计算
- 【推荐】大数据量查询要采用分页方式优化
- 【推荐】尽量使用批处理，减少访问数据库的次数，因为利用批处理能减少程序与数据库的交互,对语句的性能有很大帮助。实现批处理的方式有：1)    批插入、批修改；2)    批操作尽量提供批量接口；3)    使用in子句和临时表实现批处理。
- 【推荐】进行关联查询时，应尽量保证相互关联的表和字段的字符集一致，以防止因为字符集不一致导致的隐式数据类型转换造成索引失效。（这个主要是为了防止跨库关联查询或建视图产生效率问题，同一个库上面的规则已经要求字符集一致了。） 
- 【推荐】开启事务对多张表更新、删除时，对表的访问次序尽量保持一致，避免死锁或阻塞问题产生
- 【推荐】推荐通过查看执行计划（mysql: Explain、sql server: SET SHOWPLAN_XML ON、Oracle: explain plan for），来指导Sql语句的优化

# 操作规范 

- 【强制】所有的重要变更必须做好备份及恢复预案
- 【强制】所有的改表结构、加索引等操作都需要评估风险，预留评估、优化和审核的时间
- 【强制】批量导入、导出数据必须提前评估数据库的吞吐量和可用性
- 【强制】禁止在线上从数据库端执行后台管理和统计类查询
- 【强制】禁止有超级权限的应用程序账号存在
- 【强制】推广活动或上线新功能必须提前进行流量评估
- 【推荐】不在业务高峰期批量更新、查询数据库
- 【推荐】大批量导入导出数据时应尽可能关闭无用的日志。（目前有很多应用基于MySQL的binlog，这种日志是有效的，应具体问题具体分析。）

# 多数据库适配要求

## 背景要求

BIP产品在专属化版本要支持多种数据库，如：pg、oscar、达梦、oracle、mysql、sql server等。一方向通过平台的数据库翻译工具来作支撑，另一方面则需要各领域开发尽量按标准sql语法来完成业务开发。以下是几点涉及多数据库适配，因不同数据库差异要统一做的专项修改。后续持续补 充，在线地址：https://docs.diwo rk.com/l/A3a6F77BA81a

## 严格使用select * 

1.领域检查代码中的sql，将select *改成具体字段。

2.MDD框架已经将queryschema的addselect(*)转成了全字段，但如果同时也使用了group by，就要明确改成查询具体字段，有group by的话就会违反group by排序要求。

## 数据表必须有主键

1.增加创建主键的语句（如果涉及表中数据量很大，就需要联系运维统一操作）

2.对于表中列全部是主键的表，专属化脚本必须是INSERT IGNORE,禁止REPLACE INTO。

## 避免类型转换

## 6.11 禁止使用replace into ... select...语句

问题：多数据库适配原因，dm数据库中不支持replace into ... select ...语法

错误示例：replace into ab (x,y,id) select x,y,id from aa union all select x,y,id from bb;

**修改建议**：改成先delete然后再insert into ... select ...

delete from ab where id in (select id from aa union all select id from bb);

insert into ab (x,y,id) select x,y,id from aa union all select x,y,id from bb;

此外，为了避免去自增主键后带来的数据覆盖问题，replace into ...语句，需要在replace into脚本之前加上注释，示例：

-- beginBatch

-- WITH_UC(唯一索引列)

-- endBatch

如：

-- beginBatch

-- WITH_UC(code)

replace into table1(id,code,...) value (1,1,...);

-- endBatch

详见：https://uap-wiki.yyrd.com/pages/viewpage.action?pageId=162354760

## 6.12 字段类型为text的需要增加：COMMENT 'oracle:clob' （刘超）

**问题：**多数据库适配原因，字段类型为text的字段，在dm中翻译为varchar（8188）了，并且使用了using long row ，这样能存储超过 8188个字符。翻译为varchar的原因是有的需要在text进行比较，而达梦不支持text的比较，所以翻译为varchar；

**案例**：车间管理抽取的角色工作台的sys_portal_apply中字段content为text类型，存储的内容已经超过了9000，导致在达梦环境安装时报错，经过分析，提示内容过长字符被截断了。

**解决方案**：需要给mysql的脚本增加：COMMENT 'oracle:clob'  这样就会翻译为text了。并且不能对这个text类型的字段进行比较

## 6.20 关联更新set 列必须别名

问题：关联更新set 列必须别名！！

错误脚本示例：下面的sql虽然表名后加了别名，但是要更新的字段前没有别名，导致错误

UPDATE billitem_base t1
    left join bill_base t2
on t1.iBillId = t2.id
    set cFieldName = 'product.manageClass.name'
where t1.cName = 'productClassName' and t2.cBillNo = 'qms_warehouse_check_expire_list'

解决方案：关联更新时表名和列名前都加上别名，如下：

UPDATE billitem_base t1
    left join bill_base t2
on t1.iBillId = t2.id
    set t1.cFieldName = 'product.manageClass.name'
where t1.cName = 'productClassName' and t2.cBillNo = 'qms_warehouse_check_expire_list'
